# c4 社群信号模块——温度计（形态 A）+ 讯号汇总（形态 B）

## 0. 形态路由

| 形态 | 触发 | 产出 | 额度 | 何时用 |
|---|---|---|---|---|
| **A 温度计** | 「溫度計」「热议标的」 | 选 Top 3-5 标的，逐个三格交叉 | ≈4-6 | 想深挖少数标的时；要跨源打架叙事时 |
| **B 讯号汇总** | 「訊號彙總」「交易员在说什么」「策略信号总结」 | 全市场喊单按标的聚合成一篇 | ≈2 | 想给社群一份"这周大家在聊什么"的全景时 |

两种形态共用同一批数据源与全部防坑规则（第 3 节），差别只在聚合粒度：A 是纵向深挖、B 是横向铺开。默认 A；触发短语含"汇总/总结/在说什么"路由到 B。

本 skill 仅供社群运营人员触发使用（群成员不直接交互），周跑，可事件驱动加跑——比如 c5 热点扫描判定某标的适合并回温度计时，可临时对该标的单独加跑一次，不必等到下周固定档期。产出单篇贴文，分两段：总览段是近一日推特在吵什么（喊单聚合榜 + 多空比；喊单上游只有 24h，见第 1 节）；主体段是对喊单榜 Top 3-5 逐个给出温度计三格——🐦 推特情緒 / 💰 真金白銀 / 🏢 內部人動向三个维度交叉比对，跨源打架时明写、不硬圆。frontmatter description 已点明本 skill 的定位边界：只呈现温度、不给跟单指令——三格读数即使全部指向同一方向，也不能因此写出"所以应该跟上"这类结论句（S-6 禁令镜像，见第 2 节收尾）。

## 1. 调用序列（≈4-6/周，可事件驱动加跑）

调用序列：

| 步骤 | 调用 | 额度 |
|---|---|---|
| 1 | `signal(categories=["kol_call"], query="consensus", asset_type="tradfi")` 喊单聚合榜（总帖数 / 多空比 / top_calls） | 1 |
| 2 | 对喊单榜 Top 3-5 逐个 `signal(keywords=["<TICKER>"], categories=["kol_call","insider_trading","trader_position"], asset_type="tradfi", limit=50, verbosity="concise")` 三类钻取（**不带 time_range**；**必须 limit=50**，见下；三类一次调用仍只计 1 额度；c4 不使用 13F，不列 institutional） | 各 1 |
| 3 | （可选）`news(query="<TICKER> <公司名>", sources=["twitter"], time_range="24h")` 补推特层原文 | 0（实测） |

signal 工具有四个类别：kol_call（喊单）、trader_position（实盘持仓）、insider_trading（内部人+国会议员交易）、institutional（13F 机构持仓）。**2026-10-01 实测三点，旧 N-4"不带 categories 一次拿全四类"已失效**：① 不传 categories 的 `query="consensus"` 只返 kol_call 一类；只传 ticker 不传 categories 返回空（`no_match`）——所以步骤 2 必须显式列出所需类别（c4 用 kol_call / insider_trading / trader_position 三类），一次调用仍只计 1 额度。② **喊单上游只覆盖最近 24 小时**：传 `time_range="3d"` / `"7d"` 返回的仍是 24h 口径并标 `partial`（warning 原文：`KOL upstream covers only the latest 24 hours`），这也解释了旧 N-13"3d 与 24h 结果完全一致"。对外表述一律写「近一日」，不写「本週」「近 7 天」。③ **多类钻取不要带 time_range**：内部人按 transactionDate 过滤后窗口内没有就整类消失（13F 带窗口会被整类拒绝 `parameter_unsupported`，c4 已不用 13F）。内部人的时间窗口改在客户端按 `transactionDate` 过滤。

步骤 2 返回的 kol_call 行**不会按 ticker 过滤干净**（实测查 MU 混入 NBIS / NOW / CTKB 的帖子）——写作前必须按 `symbol == <TICKER>` 自行筛行。trader_position 在多数美股上没有数据（实测 MU / SNDK 均不返回该类；2026-10-05 实测 MU / SOFI / VST / CBRS / NKE 五只全部不返回，`status` 仍是 `ok`），返回里没有这一类就是没有，「真金白銀」格按第 3 节的降级规则处理。

**步骤 2 为什么必须 limit=50（2026-10-05 实测）**：limit 对每一类分别生效，加大仍只计 1 额度。默认 10 行时会出两种截断：① kol_call——一条列了很多只票的帖子会拆成很多行，把目标票自己的行挤出去（实测 SOFI：默认 10 行全是同一条 11 只票清单帖拆出的 CRWV～UBER，按字母序截到第 10 行，`symbol=="SOFI"` 筛完为 0；limit=50 后出现 2 行 SOFI，其中一条带目标价）；② insider_trading——10 行只回溯到 3 周前，90 天窗口内的卖出被漏掉（实测 SOFI 漏了两笔 S-Sale）。**截断自检**：内部人返回最旧一行的 `transactionDate` 若晚于 90 天窗口起点，说明还没回溯完，不能写「近 90 天只有这些」。

**Top 3-5 怎么选（2026-10-05 实测）**：`top_calls` 并列时服务端排序不稳定——同一池子两次调用，4 只并列 2 次的票顺序不同。并列时依次按 A 级以上帐号数、独立帐号数排；**进入主体段的门槛是独立帐号 ≥2 或独立帖 ≥3**（按步骤 2 筛行 + `source_url` 去重 + 数 `username` 得出），不够的只在总览行写「並列」，不展开三格。实测周末池子 Top 5 里有 4 只各 2 帖、且都出自同一个帐号——这种不够格，宁可只出 1-2 只。

frontmatter 的 mcp 声明含 `mcp__followin__metrics`，但上表三步核心序列本身不调用它——若运营想在温度计贴文里额外给某标的加一行即时价格/涨跌幅做视觉锚点，可选调用 `metrics(keywords=["<TICKER>"], query="行情", asset_type="tradfi")` 补一次快照（快照没有涨跌幅字段，自算 `change ÷ previousClose × 100`；**写明快照时点**——周末与美股开盘前 `as_of` 停在上一交易日收盘，`change` 是那天的涨跌，对外写「上週五收盤」这类时点，不写成「今天」；盘前/夜盘涨幅只能引 `extendedHoursQuote`）（不计入标称额度 ≈4-6/周，需另计 1 点）；没有这类展示需求时，三步核心序列完全不需要 metrics。

调用形态铁律（本序列全程通用）：

> **调用形态（2026-10-01 实测，取代 2026-07-20 的"数组被拒、只能 query 串"铁律）**：入参分工是 **`keywords` 数组放标的、`query` 放意图词、`categories` 指定类别**。`signal` 现在必须显式传 `categories`——只传 ticker 不再自动展开四类，返回空并带 `no_match`。每次调用最多 5 个 keywords，超出或解析不了的项写在 `meta.warnings`，**调用后读一遍**，缺的分批补。单批并行 ≤4 路（SSE 红线）。客户端不接受数组入参（报 `-32602`）时，可退回 `query="<TICKER> consensus"` 这类拼串（实测仍能解析），但多类钻取没有等价的 query 串写法。另：Followin session 每 5-8 次调用可能短挂，重试 1 次即恢复，还不行让运营 `/mcp restart followin`。

每步 query 主形态调用示例：

```
1. signal(categories=["kol_call"], query="consensus", asset_type="tradfi")
   # 喊单聚合榜，1 额度；口径是最近 24 小时

2. signal(keywords=["<TICKER>"], categories=["kol_call","insider_trading","trader_position"], asset_type="tradfi", limit=50, verbosity="concise")
   # 对步骤 1 喊单榜 Top 3-5（按上文门槛筛过）逐个钻取，温度计三格的素材皆出自这一步；不带 time_range；
   # limit=50 防截断（默认 10 会把目标票的喊单行和 90 天内的内部人行挤掉）；
   # kol_call 行按 symbol == <TICKER> 自行筛，再按 source_url 去重、数独立帐号；要更完整的原帖可加 query="详细仓位"
   # Top 5 时按 SSE 红线单批 ≤4 路，拆成 4+1 两批并行

3. news(query="<TICKER> <公司名>", sources=["twitter"], time_range="24h")
   # 可选，补推特层喊单帖原文；quota=0（实测）
```

## 2. 产出模板：温度计三格

spec 产出结构（逐字）：

> 产出结构：近一日推特在吵什么（喊单聚合榜 + 多空比）→ 每个标的的温度计三格：
> - 推特情緒（喊单方向比 + A 级 KOL 代表观点，正反都放）
> - 真金白銀（实盘持仓方向/人数/杠杆——数据薄就明说薄）
> - 內部人動向（近 90 天 S-Sale/P-Purchase，剔除 F-InKind）
> → 跨源打架时明写结论（"情緒滿格 ≠ 大錢進場"）→ 名词卡。

（spec 原文此处写「本周推特在吵什么」；2026-10-01 / 10-05 实测喊单上游只有 24h，已改为「近一日」。标题里的「本週」只代表发布节奏，正文一律写「近一日」。）

落地结构：

1. **标题**：📌 + 本週熱議溫度計 + 日期区间（「本週」只指发布节奏）
2. **一句話先懂**（≤40 字）：近一日喊单最热的 1-2 个标的 + 整体多空比一句
3. **模块正文**，分两段：
   - **总览段**：近一日推特在吵什么——喊单聚合榜（Top 3-5 标的排名，并列照实写「並列」）+ 整体多空比一行，素材来自步骤 1 consensus 返回的聚合结果。**consensus 的计数按拆行算，不按帖子**（2026-10-05 实测：`total_posts:34`，按 `source_url` 去重后只有 24 条帖子；一条 11 只票的清单帖贡献了 11 个 bullish；buy 并进 bullish、sell 并进 bearish）——所以总览行写「多空提及比 X:Y」，不写「N 則喊單」；要写「N 則」须另跑形态 B 步骤 2 去重后自算
   - **主体段**：对总览榜单 Top 3-5（按第 1 节门槛筛过）逐个给出温度计三格，每个标的固定三行：
     - 🐦 **推特情緒**：喊单多空比（如"多 8：空 2"，按筛行 + `source_url` 去重后的帖数）并注明「來自 K 個帳號」——同一帐号多帖不能写成「多人看多」；一帖列 ≥5 只票的清单帖只计入统计、不作代表观点 + A 级 KOL 代表观点正反各一句，注明 tier（如"（A 級 KOL）"）——正反都要放，不能只挑一边；反方只有 B 级帐号时写「反方僅見 B 級帳號 N 則」，不引原话
     - 💰 **真金白銀**：实盘持仓方向/人数/杠杆一句；统计前先过滤 tier 为空、notional 为 null 的行（第 3 节镜像）；标的属 stock_perp（代币化股票永续）时标注「鏈上股票永續交易員」而非「美股交易員」；过滤后样本仍太薄就直接写「本週實盤數據樣本太薄，不足以下判斷」，禁止硬凑（S-7 铁律 3 镜像）
     - 🏢 **內部人動向**：近 90 天窗口，客户端按 transactionDate 过滤（第 3 节 N-6 镜像），只认 S-Sale（卖出）、P-Purchase（买入）两种；90 天内无符合条件记录就写「近 90 天無內部人申報異動」（先过第 1 节的截断自检）；同一返回里的议员交易（带 `_chamber` 字段）按第 3 节议员规则另起半句
4. **接下來看什麼**（可选）：若某标的三格分歧巨大，提示下次跑温度计时留意哪个维度会不会收敛
5. **今日名詞卡**
6. **免责声明**（S-11 对外版逐字）："⚠️ 以上整理自公開研報與市場數據，僅做資訊分享，不構成投資建議。"

跨源打架收尾句（两种场景，按三格实际读数择一或改写，不是唯一措辞）：
- 情绪与资金背离（推特情緒火热、真金白銀没跟上）→「情緒滿格 ≠ 大錢進場」（spec 逐字句式）
- 三格互不指向同一方向（无法收敛成一个判断）→「三個溫度計指向不同方向時，別把任何一個當聖旨。」
结论必须诚实反映三格各自的实际读数，不能为了叙事流畅硬圆成一个方向（S-5 多空平衡镜像）。

若推特情緒或內部人動向行引用到具体价格、目标价或涨跌幅数字（如某 KOL 喊单帖提到的目标价、或内部人申报的交易金额），这些数字只能引用本次调用返回值，KOL 转述或新闻里的二手数字必须先经快照核实才能写——呼应 S-7 铁律 2（原文：铁律2 价格：当前价/涨跌幅只引本次 MCP 返回值；新闻与 KOL 转述的百分比是二手，必经快照核实）。核实时写明快照时点（如「上週五收盤」）；KOL 说的夜盘/盘前涨幅与 `extendedHoursQuote` 算出来的对不上就不写。

**字段先对原文再引（2026-10-05 实测）**：`target_price` 与 `direction` 都是机器抽取的，引用前对照 `content`——① 假设性估值不写成目标价（实测某帖原文是「如果市场给 MU 和 NVDA 一样的倍数就会到 $3,210」，`target_price` 却是 3210；反过来另一帖明写「$800–1,000 樂觀情境」，字段是 null）；② 看空标签要读原文确认是看空标的本身（实测一条被标 bearish 的帖子，原文是「别追 IPO，但公司业务更强了」）。

**只呈现温度、不给跟单指令**（frontmatter description 定位）：三格读数即使全部指向同一方向，也不能写出"所以应该跟上/建议加仓"这类结论句——skill 只负责客观呈现三个维度各自的读数，买卖判断留给读者自己；给买卖指令、给仓位建议是 S-6 禁令的红线（原文：不给买卖指令、不给仓位建议、不预测短线涨跌；禁用"必涨/起飞/上车/梭哈/抄底"），本 skill 尤其容易因为"三源共振"而忍不住多说一句，需格外注意收住结论。

字数：单篇 500-800 字（S-4 默认档，c4 未被列为例外）。Top 3-5 标的每个三格若导致超长，运营可只保留 Top 3 出稿，Top 4-5 留作候补下周再跑，不必为了凑够 5 个硬塞。

以下是结构示范样例（非实测数据，实现时按当次调用返回替换；排版规则不变——纯文字＋emoji，不套 markdown 加粗/标题/表格，层级靠 emoji ＋ 空行 ＋「｜」——S-9 镜像）：

```
📌 本週熱議溫度計｜7/20–7/26

一句話先懂：近一日推特喊單最熱是 MU（9 則全多），但真金白銀沒跟上，情緒溫度和實盤資金出現落差。

近一日推特在吵什麼
喊單聚合榜：1️⃣ MU　2️⃣ SPCX　3️⃣ NBIS｜整體多空提及比 12:1，情緒偏熱

MU 溫度計
🐦 推特情緒：多 9：空 0（來自 4 個帳號）｜正：算力型 KOL（A 級）「DRAM 漲價週期才剛開始」｜反：暫無明顯反方聲音，一面倒偏多本身就是風險訊號
💰 真金白銀：實盤僅 1 位交易員輕倉做多，槓桿 2x｜過濾無評級與空值後樣本仍偏薄，本週實盤數據樣本太薄，不足以下判斷
🏢 內部人動向：近 90 天僅 CEO 兩筆 S-Sale（賣出），無 P-Purchase

跨源打架：情緒滿格 ≠ 大錢進場——推特一面倒看多，但真金白銀和內部人動向都沒有同步跟上。

接下來看什麼：留意真金白銀下週是否回補，若持續背離，這波情緒面可能只是噪音。

今日名詞：真金白銀
交易員拿自己真實資金開的實盤倉位，和「喊單」不同——喊單可能只是嘴上看好，真金白銀才是拿錢投票。可以粗略理解成：聽人講不如看他自己敢不敢下注。

⚠️ 以上整理自公開研報與市場數據，僅做資訊分享，不構成投資建議。
```

## 2.5 形态 B · 讯号汇总（市场级策略聚合）

### 调用序列（≈2 点）

| 步骤 | 调用 | 额度 |
|---|---|---|
| 1 | `signal(categories=["kol_call"], query="consensus", asset_type="tradfi", time_range="24h")` 拿聚合口径（总帖数/多空比/Top5 标的） | 1 |
| 2 | `signal(categories=["kol_call"], query="详细仓位", asset_type="tradfi", time_range="24h", limit=50, verbosity="concise")` **不带 ticker** → 全市场原帖（旧实测曾带 `status:"partial"`；2026-10-05 实测为 `ok`） | 1 |

**步骤 2 按 limit=50 拉全量**（2026-10-05 实测）：24h 池子通常不到 50 行，limit 数的是**拆行后的行**，不是帖子，而且 limit 小于池子时返回的**不是最新的 N 行**——旧写法 limit=20 返回 20 行只对应 15 条帖，漏掉了当期唯一一条看空帖，「空方」段因此写不出来；limit=50 返回 34 行，正好等于步骤 1 的 `total_posts`。**自检**：返回行数应等于步骤 1 的 `total_posts`，对不上就说明截断了。体积随池子大小浮动（实测 34 行 + concise 约 2.5 万字符；2026-07-23 旧实测 139 行 13.7 万字符，N-20），仍然**禁止直接读入上下文**。正确做法是客户端脚本聚合后只保留结构化摘要：按 `source_url` 去重（N-5：一条帖子会按提及的每个标的裂成多行，实测 139 行 → 96 条独立帖）→ 按 `symbol` 分组统计多空 → 提取 `conviction`/`target_price`/`is_recommended`/`kol_info.tier` → 只把摘要交给写作层。

### 聚合规则（决定这篇的成色）

1. **按标的分组**：`direction` 归三类——多（bullish/buy）、空（bearish/sell）、中性；统计每组的 A 级以上帐号数和**独立帐号数**。对外的「N 則」和多空比一律用去重后的帖数自算，**不直接抄步骤 1 的 `total_posts` / `bull_bear_ratio`**——那两个按拆行计（2026-10-05 实测 34 行 vs 去重 24 帖）。同一帐号多帖不能写成「多人看多」；一帖列 ≥5 只票的清单帖只计入统计，不作代表观点。
2. **分歧检测（本形态的核心）**：同一标的同时有多和空 → 单独成段，**排在热度榜前面**。一面倒的标的信息量低（大家在讲同一个故事），分歧才是真信息。
3. **空方观点必须单独成段**：空方在原始数据里天然是少数（实测 111 多 vs 10 空），不单列会被淹没。板块级的看空判断（如"做多软件、做空芯片"同时点名多只芯片股）优先收录——它常常和热度榜的一面倒直接冲突，把两者并排放是最有效的风险提示。收录前读原文确认 `direction` 标签（见第 2 节「字段先对原文再引」）。
4. **操作动作单独列**：`direction` 为 buy/sell 且文本含止盈/离场/进场提示的，比单纯的"看多/看空"更有信息量。
5. **分级过滤**：正文只引用 A/A+ 级帐号的观点；B 级及以下只计入统计不引用。某标的的反方（或当期空方）只有 B 级帐号时，写「反方僅見 B 級帳號 N 則」，不引原话、也不省略这个事实。

### 本形态专属红线

- **喊单 ≠ 研报**：本形态出现的目标价一律标明是喊单者自己给的；与 c3 的券商目标价不能混排、不能合并计算区间。`target_price` 字段引用前对照原文，假设性估值（「如果给同样倍数就会到 $X」）不算目标价（第 2 节）。
- **喊单 ≠ 实盘**：结尾第 ③ 条提醒为必带项。当期实盘数据薄时（实测 2026-07-23：谷歌特斯拉财报夜当晚，美股实盘零仓位）必须点明，这是对"跟单"最有效的降温。
- **一面倒要说破**：某标的 N 多 0 空时，不能只写"市场看多"，要写"沒有任何一則看空——這種一面倒本身就值得留意"（S-5 多空平衡在本形态的执行方式）。
- **窗口用词（2026-10-01 实测更正 N-13）**：喊单上游只覆盖最近 24 小时，传 3d / 7d 返回的仍是 24h 口径（响应会标 `partial` 并写明原因）。贴文里推特情绪的时间表述写「近一日」；标题里的「本週」只指发布节奏，**正文不得把 24h 的喊单计数写成「本週 N 帖」**。
- 分级、去重、议员交易识别等其余规则同第 3 节，两形态通用（c4 不使用 13F，见第 3 节）。

## 3. 防坑镜像

spec 逐字 6 条防坑规则（详见 caveats SSOT §6 N 系列 + 已知问题登记）：

> 防坑规则（本次实测新增，详见 §6）：
> - kol_call 按提及展开，一条推文裂成多行：按 source_url 去重、按 symbol 字段归属（N-5）。
> - insider/congress 行无视 time_range，必须客户端按 transactionDate 过滤（N-6）。
> - 13F 申报季中期数据残缺，禁止引用环比（N-7）。
> - trader_position 过滤 tier 为空/notional null 的行；美股覆盖日级剧变，只能当天现拉、按 underlying 合并符号分裂（既有 caveat）。
> - **统计人数前必须做交易员身份归一，且是双向的**：显示名既会「同人两名」也会「同名两人」（N-59n / N-59s）——按 `profile` 指纹判，不用 `trader` 字符串。
> - stock_perp 是代币化股票永续，呈现时标注"鏈上股票永續交易員"而非"美股交易員"。
> - signal query 不放"KOL"等元词（会被解析成 crypto 关键词，实测空返）。

逐条展开：

- **kol_call 去重+归属（N-5）**：

  > N-5：kol_call 原帖按提及 fanout 成多行（同 URL 不同 symbol/方向）；按 source_url 去重、symbol 字段归属（实测 2026-07-22）。

  步骤 1/2 返回的 kol_call 类数据，同一条原始喊单推文可能因为提到多个标的被拆成多行（同一个 source_url，symbol 或方向字段不同）。总览段的喊单聚合榜排名、以及每个标的推特情緒行的多空比统计，都必须先按 source_url 去重，再按 symbol 字段把行归属回正确的标的——不去重会让同一条推文的热度被重复计入喊单榜排名，虚增某个标的的讨论热度。

- **insider/congress 客户端过滤 transactionDate，只认 S-Sale/P-Purchase（N-6）**：

  > N-6：insider/congress 行无视 time_range（7d 返回 2020 年记录）；客户端按 transactionDate 过滤强制（实测 2026-07-22）。

  內部人動向行必须客户端按 transactionDate 过滤——API 不管 time_range 传了多少，insider/congress 类的行照样可能混入多年前的旧记录。c4 的窗口是近 90 天（不同于 c1 早报镜像 N-6 时用的"昨日"单日窗口——本 skill 是周跑产品，要给一个有意义的近期趋势而不是单日快照，二者窗口不同是有意为之，不要混淆）。过滤后只认 S-Sale（卖出）、P-Purchase（买入）两种交易类型，其余类型一律不计入——既有 insider 条目的扩充解读规则说明了原因：F-InKind/M-Exempt 为缴税代扣非主动交易；对外表述"内部人卖出"只认 S-Sale，买入只认 P-Purchase。

  **议员交易另按字段识别（2026-10-05 实测，字段口径与 N-95 / N-137 一致）**：同一返回里带 `_chamber` 字段的行是议员交易，没有 `transactionType`，上面的 S-Sale / P-Purchase 规则会把它悄悄丢掉。按以下处理：`type` 为 Purchase / Sale 的计入；窗口仍按 `transactionDate` 过滤（实测 MU 一笔交易日 07-10 在窗口内，另一笔交易日 07-06 在窗口外、但 08-12 才披露——按交易日算不计入）；对外写「X 日交易、Y 日披露」（`disclosureDate`），金额只写区间（`amount`，如 $1,001–$15,000），与公司内部人分句写，不合并计数。

- **c4 不使用 13F（N-7 加 2026-10-05 实测）**：

  > N-7：13F institutional 申报季中期 investorsHolding 环比为残缺假信号（实测 NVDA 6234→1441）；申报季内禁止引用环比（实测 2026-07-22）。

  旧版本模块的做法是"一律不引环比、只引绝对持仓数字（如'目前 X 家机构持有'）"。2026-10-05 实测这条也站不住，步骤 2 因此不再列 institutional：① 返回只有前 10 名持有人（`is_exhaustive:false`，`provider_row_count` 是上限 100 而非真实家数），**算不出"几家机构持有"**；同一机构还会重复出现两行；② 每季结束后的头几周，返回会**整页切到新季度**，只剩零星早报机构——实测 10-05 VST 只有 1 家、NKE 只有 2 家，且持股都是 0（已清仓的早报户），在 query 里写上一季日期也拉不回旧季度；③ 三格模板本来就没有 13F 的位置。任何 13F 数字放进温度计都可能是假信号。

- **trader_position 当天现拉 + underlying 合并（既有 caveat）**：

  > trader_position 美股标的覆盖**日级剧变**（实测 07-09 MU 4 人 vs 07-15 MU 1 人、海力士从无到 3 人）；且同一标的可能符号分裂成多组（海力士 underlying=000660.KS 散在 SKHYNIX/SKHX/SKHY 三个 symbol）。Workaround：任何对外用途都当天现拉；空 keywords 拉 trending 看当前有货标的；符号分裂需按 underlying 合并（数据特性，非 bug）。

  真金白銀行统计前先过滤 tier 为空、notional 为 null 的行；美股标的的实盘持仓覆盖会逐日剧变，产出前必须当天现拉，不能沿用几天前甚至上周跑过的缓存数据；同一标的可能因符号分裂成多个 symbol（如海力士拆成 SKHYNIX/SKHX/SKHY），统计人数/方向/杠杆前要按 underlying 字段合并，否则会把同一批交易员的仓位重复计成好几个不同标的。

  **tradfi 热门榜里混着加密币（2026-10-05 实测）**：空 keywords 拉 tradfi trending 时，SUI（入场价 1.25）、LIT（入场价 3.83）被标成 `asset_type:"tradfi"` + `instrument_type:"stock_perp"`。`entry_price` 量级明显不像该代码对应股价的，按加密币处理，不进真金白銀行，也不标「鏈上股票永續交易員」。

- **交易员身份归一必须双向做（N-59n / N-59s，2026-08-04 实测）**：

  > 显示名**两个方向都不可靠**，且**同一份返回里两种情况会同时出现**：①**同人两名**——两条不同显示名的 `profile` 逐字段相同，连 `summary_refreshed_at` 都是同一秒；②**同名两人**——同一个显示名出现两次而 `profile` 完全不同（实测一条 tier A/151 笔，另一条 tier —/0 笔）。
  > ✅ 服务端内部身份是对的（`active_trader_count` 把同名两条算作 2 人），只是没暴露 ID。

  本模块「真金白銀」行要统计**几个人**在做多/做空，所以这一步绕不开：**按 `profile` 指纹归一**（`overall.n_trades` + `overall.net_pnl_usd` + `summary_refreshed_at` 三元组），**指纹相同就合并（哪怕名字不同），指纹不同就拆开（哪怕名字一样）**。
  ⚠️ 这与上一条的 `underlying` 合并是**两件独立的事**：那条合并的是**标的**（同一只票的符号分裂），这条合并的是**人**。只做前者仍会把同一个人在多个符号下的仓位算成好几个交易员。
  ⛔ 归一后如果确实存在同名两个账户，产出里**不要写成两个交易员**，也不要合并——按"同名两个账户"处理，或直接只报归一后的人数、不点名。

- **stock_perp 标注「鏈上股票永續交易員」**：

  > stock_perp 是代币化股票永续，呈现时标注"鏈上股票永續交易員"而非"美股交易員"。

  真金白銀行若命中的持仓类型是 stock_perp（代币化股票的链上永续合约，而非真实美股经纪商持仓），呈现时必须标注"鏈上股票永續交易員"，不能写成"美股交易員"——两者交易的是完全不同的资产，混为一谈会让新手误以为这是真实美股仓位。

- **signal query 禁放"KOL"等元词**：

  > signal query 不放"KOL"等元词（会被解析成 crypto 关键词，实测空返）。

  步骤 2 的标的放 `keywords`，query 只放"详细仓位"这类意图词，禁止把"KOL"这类元描述词塞进 query——会被服务端解析成加密货币关键词，实测直接空返，多类钻取全部落空却不会报错，容易被误判成"这个标的没有信号"而错误放弃该标的。
