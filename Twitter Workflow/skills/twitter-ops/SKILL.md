# Twitter 日运营 — 主调度中心

工作流调度器。只管三件事：**怎么串联子 Skill**、**在哪停下来等人**、**用哪种模式跑**。

> Skill 全景图与职责表见仓库 `README.md`，本文件不重复。

## 0. 开工前的配置锚点

### 🚧 第一步永远是：检查初始化状态

#### 判定原则（先读完这几条，再看表）

**① 只检"必填项"，不检整份文件。**
配置文件是**分阶段填**的——`config.md` 明写「先只填 🔴 三项」、`operations-plan.md` 明写「第一次只填 §二 §七」。
**按文件整体判"有没有占位符"会把合法的分阶段状态判成未初始化**，用户照指引做完仍被拦死。
→ **判定范围只包括下表列出的字段/小节**；范围外仍有占位符是正常的，不阻塞。

**② 占位符的两种形态都要认，且方括号要认全。**
- 下划线形态：`___` / `@___`
- 方括号形态：**任何被反引号或行内包裹的 `[中文或英文]`**，如 `[你的账号]` `[数字]` `[主领域]` `[说明]` `[待填]` `[例：…]`
  ⚠️ **不要只认 `[你的` / `[数字]` 这几个前缀**——`[主领域]` `[次领域]` `[核心KOL…]` 全在名单外，会让空文件判成已填。
  ⚠️ 排除 markdown 复选框 `[ ]` / `[x]`。

**③ 🔑「文件存在但仍是占位符」= 视同没有（通用规则，全仓适用）。**
所有写着「文件不存在 → 降级/warn/跳过」的规则，**必须同时判占位符未替换**。
新克隆时这些文件**全都存在**，逃生条款按字面永不触发，模型会把 `[主领域] 50-60%` 当真配置读进去——
**这比硬闸更危险：它不拦你，直接产垃圾。**

**④ 🔑 出厂默认值长得像真配置——靠语法抓不到，改用显式状态位。**
最危险的一类不是占位符，是**无标记的默认值**：`operations-plan §三` 写着 `锐评 25% / 主引擎 ≥3 条 / 合计 ≥70%`，
**一个方括号都没有**，而 topic-engine 自查③ 拿它当硬闸——用户从没选过的数字被当成他的决定执行。
→ 约定：凡是出厂默认值的小节，顶部带一行

```
<!-- INIT-STATUS: template-default — 出厂默认值，未经用户确认。用户改过本节后请删掉这一行。 -->
```

**读取方带这行 = 视同未配置**，按该项的 n/a 逃生处理并在输出标注「配比用的是出厂默认值」。
这样「未初始化」是**可读取的事实**，不再靠猜语法。

#### 判定范围（只检这些）

| 必检项 | 没填的后果 |
|---|---|
| **`config.md` 的 🔴 三项**（`ACCOUNT` / `STATE_DIR` / `BRIEF_DIR`）| `ACCOUNT` 空 → 所有拉自家数据的调用直接失败；目录空 → 候选池无处落盘，下游扑空。⚠️ **同时检目录不能指向 `/tmp`**（config.md §校验 自己声明的规则）——重启即清，跨天资产全丢 |
| `references/operations-plan.md` **§二**（每日配额）| 不知道该出几条，会一直出稿 |
| `references/operations-plan.md` **§七**（风险红线）| 不设红线 |
| `references/voice-guide.md` 的 **❌「不能做」那节** | 无内容红线；其余节留空只降质量，不阻塞 |

> **范围外一律只 warn 不拦**：config.md 🟡 区、operations-plan §一/§三/§四/§五、voice-guide 其余节。
> 它们缺失会降低产出质量，输出时如实标注即可——**别把"能跑得更好"写成"不许跑"**。

### 🕐 配置闸过了之后的第一个动作：取一次当前时间，向下游传

（这不是一条"判定原则"——上面 ①-④ 讲的是"怎么判断配置有没有填"，这一节讲的是"开跑第一步做什么"。）

```bash
DATE=$(date +%F)           # 2026-07-30
WEEK=$(date +%G-W%V)       # 2026-W31 —— ISO 周，跨年不漂
NOW_MS=$(( $(date +%s) * 1000 ))
```

🔴 **禁止凭模型自己的日期认知推算日期或周数**，也禁止让每个下游 Skill 各自猜——
调度器取一次，整轮所有 Skill 用同一组值。这几个值被当**文件名**用：猜错 → 写进错误日期的文件 →
下一轮查重扑空、读不到今日产物、回填链断，而**全程不报错、产物格式齐全**。
各 Skill 自己的 §0 也各有一条同样的时钟条款（它们可以被直接触发、不经本调度器），
两处规则必须一致：**周编号只认 `%G-W%V`**。

**⚠️ 一次只跑一轮。** 这套东西没有文件锁，日简报、`-latest.txt`、`last-refresh`、
弧线计数、周配额全是读-改-写或追加。并发跑不会报错，只会让下一轮读到错的数。

**检测到未初始化时，不要继续跑流水线。** 改为输出：

```
🚧 检测到配置尚未初始化，先花几分钟把这几项填上，否则跑出来的东西用不了。

必填（不填没法跑）：
1. **config.md 的 `ACCOUNT`** —— 你的 @handle。所有自家数据分析都锚在它上面（这是唯一权威，别填到别处）
2. operations-plan.md §七「风险红线」—— 什么绝对不能发
3. operations-plan.md §二「每日配额」—— 每天出几条

强烈建议（决定产出质量）：
4. voice-guide.md —— 你的人设语气

💡 这几份文件里都写了「怎么填」。voice-guide 如果你有 30 条以上历史推文，
   直接说「读一下我最近 50 条推文，帮我填 voice-guide」，我从你的实际用词里归纳，
   比你自己想准。

填好后再说「跑一轮」。想先看看效果的话，可以说「只扫热点」—— 那一步不依赖这些配置。
```

> ⚠️ **别用占位符硬跑。** 拿 `@[你的账号]` 去调 API 会失败；拿模板人设写稿会产出通用垃圾。
> 用户说「先跑起来看看」时，只放行 `trend-scout`（扫热点不依赖账号配置），其余环节仍然拦。

### ⚠️ 账号锚定红线

**MCP 登录账号 ≠ 运营账号**：登录账号只决定"能不能发推"，不决定"分析谁的数据"。❌ 调 `whoami` 拿 username 当分析对象；✅ 所有拉自家数据的调用（performance-review / engagement / competitor-watch 基线）一律锁 **`config.md` 的 `ACCOUNT`**（唯一权威，operations-plan §一 只做展示不做取值），跑之前先打印 `🎯 当前运营账号：@[你的账号] / followers：[实测值]` —— 锚错了整轮数据全废。

### MCP 数据源

所有 MCP 调用走 `mcp__followin__*` 五工具：`metrics`（行情/宏观/基本面）· `news`（新闻/研报/推文）· `signal`（KOL 喊单/巨鲸/内部人）· `twitter`（账号级操作）· `subscription`（自选盯盘）。美股 / 大宗 / 宏观必传 `asset_type="tradfi"`，加密传 `"crypto"`；`news` 的 query **可空**（空 query = firehose 取 trending，实测正常返回）；`twitter` 走 `action` 路由（如 `action="user_tweets", user_name="[你的账号]"`）。

## 1. 模式控制

**一条流水线，两种跑法。**

| 模式 | 触发 | 行为 |
|---|---|---|
| 🤖 自动 | "跑一轮" / "自动跑" / 默认 | 全流程按预设规则决策，直接输出终稿 |
| 🔧 手动 | "手动跑一轮" | 每个检查点暂停，等用户确认 / 修改后继续 |
| 🔀 切换 | 自动模式中用户发消息 | 当前步骤转手动，处理完可继续自动或保持手动 |

**核心原则：默认自动，随时可拦。** 用户在任何阶段发消息 = 触发当前检查点，流程暂停等指令。
**跳节点权限（🔴 唯一权威，§2 例外条款与 §9 指令路由都以本条为准）**——按用户给了什么判，**不按他说什么判**：

| 用户给的东西 | 处理 |
|---|---|
| 自带 ≥6/7 要素（候选/Pattern/观点/数据/风险/金句/形式） | ✅ 跳采集与选题，直进 tweet-composer。输出标「自带模式」 |
| 明说"跳过 topic-engine 直接给我 X"，但**要素不足 6/7** | ⚠️ 可跳，但必须先提示「已跳过差异化检查，可能与对标账号撞车」，并在终稿里标注 |
| 只给了一个角度/主题（如"帮我写推文：美债流动性"） | ❌ **不跳**。这不是快速通道——快速通道的门槛是要素数，不是句式。走 topic-engine 出 3 角度 |
| "快速选一下" / "今天发啥直接说" | ❌ 不跳，退回逐检查点跑 |

⚠️ **§9 指令路由里「"帮我写推文：[角度]" → 直接进 tweet-composer」说的是"路由到哪个 Skill"，
不是"免检"**——tweet-composer 的 §1.1 入场硬检照跑，缺要素照退回。**路由 ≠ 放行。**

## 2. 流水线顺序硬锁

**单向有序图，不跳节点、不并行交叉**：trend-scout（简报 + candidates JSON）→ topic-engine（Top 5 × 每题 3 角度）→ 用户选定主推角度 → tweet-composer（终稿）→ 人工确认发布 → engagement（互动）+ performance-review（追踪 + 爆款入库 → Pattern 升级）→ 下轮起跑。

### 🚫 违规识别 + 应答

| 用户表达 | 违规 | 我的动作 / 回应 |
|---|---|---|
| "今天有什么选题" / "今天发什么" | 跳 trend-scout | 没简报 = 凭印象选题。"先跑 trend-scout + topic-engine 出 Top 5 给你选，约 10 分钟" |
| "随便写一条 [标的]" / "候选出来了直接写" | 跳 topic-engine | "情报 ≠ 角度 ≠ 写作。先出 3 角度备选，不然容易撞今天已发的调性 / 错过 Pattern 钩子" |
| "大概意思就是 X，直接写吧" | 不验上游入参 | 回 topic-engine 补齐 7 项入参再起草 |

另三条：用户问"你看哪条最好" → 给推荐 + 理由，但**最终由用户拍板**；复盘需 ≥5 个工作日连续数据（不足即噪声）；对标账号只能取自 `competitor-list.md` 白名单，不许现编。
上游节点缺料（简报缺分区 / 候选不足 / 每题只给 1 个角度）→ **退回该节点补齐**，不带病下传。
**例外**：见 §1 那张「跳节点权限」表——那里是唯一权威，本节不重复判据。

## 3. 节点验收 lint（缺项不准下传）

**trend-scout**：① 简报分区齐（📊 实时数据区 / 📰 叙事摘要区，数字不混用）② candidates 落盘 `$STATE_DIR/trend-scout-candidates/$DATE.json`（刷新档 `-HHMM`）**且索引 `$DATE-latest.txt` 已写、内容指向的 json 真实存在** —— 只验 json 不验索引，会出现「lint PASS 但 topic-engine 的强制读当场扑空」③ 候选数达标（首扫 ≥12 / 刷新 ≥7）

**topic-engine**：① 5 个选题块 ② 每题 3 角度备选 A/B/C ③ 每角度 5 要素齐（核心观点 / 反共识维度 / Hook / 反向风险 / 结尾金句）④ 每角度标 Pattern 编号 + 内容类型（**两轴都标**：轴 A 形态 + 轴 B 角色，见 operations-plan §三）⑤ 主推角度有打分明细 + 3 角度对比表 ⑥ 不与近 7 天已发选题撞角度 —— **数据源 = `twitter(action="user_tweets")` 现拉自家近 7 天原创推**（剔 reply 与 `RT @` / `RT@`），不依赖任何本模板不产出的历史清单文件；拉不到就记 WARN「查重未执行」，**不许当 PASS 划过去**

**tweet-composer**：① 7 项入参齐 ② 字符预算（单推 ≤280 加权；Thread 逐条核）③ 反向风险在**正文**里而不只在 metadata ④ 配图方案 + 首评草稿齐（**完整终检见 tweet-composer §9 的 [阻塞]/[披露] 清单，条数以那里为准，本处不复述**——写死条数就是漂移源，同 performance-review 那条原则）

## 4. 价格数据铁律（贯穿全流程）

1. **单一信源**：推文里任何价格 / 涨跌幅只能引用 `mcp__followin__metrics` 返回的数字，新闻标题与热榜话题里的价格一律视为"历史叙述"。
2. **简报分区**：「📊 实时数据区」只放 API 硬数据，「📰 叙事摘要区」放新闻 / 观点 / 事件并标来源，两区数字不混用。
3. **写稿前二次确认**：起草前若涉及具体价格，**重新调一次 `metrics`**，不用简报里的旧数（采集到写稿隔几分钟，价格会变）。
4. **质检核验**：检查点③ 硬性项 —— `[ ] 推文中所有价格 / 数据与最近一次 API 返回值一致`。

## 5. 主流水线：内容生产

```
[热点采集] → 检查点① → [选题排序] → 检查点② → [价格二次确认] → [撰写 + 事实核查] → 检查点③ → [终稿] → [发布后 SOP]
 trend-scout           topic-engine            metrics          tweet-composer            人工确认才发
```

### Stage 1：热点采集 → `trend-scout`
执行模式（首扫 / 刷新 / 快速 / 突发 / 补充 / 深度）由 trend-scout 定义，按用户措辞传递即可，**模式表不在本文件重复**。输出 = 热点简报（热点 + 链上异动 + 价格快照 + 宏观信号）。

**⏸️ 检查点①（热点筛选）** — 🤖 自动：按热度 + 数据密度筛 Top 3（有链上/价格数据支撑 > 纯新闻 > 纯观点；排除 24h 内发过的同类）。🔧 手动：列表等用户选。
```
⏸️ 检查点① — 热点筛选
1. 🔴 [话题A] 热度 XXX · 数据密度 高   2. 🟡 [话题B] 中   3. ⚪ [话题C] 低
回复：数字（"1 2 3"）/ "全部" / 补充话题 / "继续"用自动推荐
```

### Stage 2：选题排序 → `topic-engine`
- **时效性硬过滤**（最先跑）：>48h 淘汰；24-48h 降级保留且需 ≥2 个数据点
- **热点匮乏自动补充**：过滤后可用话题 < 2 个 → 回调 trend-scout 补扫（`news` 多 query + `twitter` 批量 + `signal`）后重新选题

**⏸️ 检查点②（选题确认）** — 🤖 自动：选 P0（最多同时推进 2 个选题）并匹配形式。🔧 手动：等用户挑角度 / 调优先级 / 指定形式。
```
⏸️ 检查点② — 选题确认
📌 P0 [话题A] · 角度[锐评] · 形式[单推] · 理由[时效强 + 数据充分]   📌 P1 … 📌 P2 …
回复："P0"/"P1"/"全部" / 调整角度 / 调整形式 / 补充指令 / "继续"
```
**形式匹配**：时效高（<2h）+ 数据少 → 单推；数据密度高 + 多维度 → Thread；借势热推 → 引用推。主流水线只产推文级内容。

### Stage 3：内容撰写 → `tweet-composer`
四种产出：单推 / Thread（原创）/ Thread（长文拆解）/ 引用推。字符预算、结构模板、事实核查 6 维归 tweet-composer，本文件不重复。

**⏸️ 检查点③（草稿审核）** — 🤖 自动：终检通过直接出终稿等发布。🔧 手动：展示草稿，回复 "OK" 确认 / 修改意见（"开头太弱，换个 hook"）/ "换个风格" / "再写一版" / "太长了"。

**硬性项**：事实核查 6 维逐条列证据（禁裸写"已过"）· 价格与最近一次 API 一致 · 反向风险在正文 · 未触内容红线 · 当日频次未超上限 · 配图方案与首评草稿齐。

### Stage 4：终稿输出
正文 + 配图方案 + 首评草稿 + 建议时段，标注"📋 可直接复制发布"。

## 🔴 发布始终由用户人工确认，不论哪种模式。任何 Skill 都不得自动发推。

## 6. 每日 MVP + 流水线 SLA

采集跑再多，没有终稿落地就是空转。
**每日 MVP**：工作日每天 **≥1 条原创主推**发出去（周末允许 skip），**完美 vs 发出去 → 选发出去**。违反信号：❌"今天没出选题明天补" · ❌"候选池没一条想发的"（强制取最高分那条走通全链）· ❌"在改 Skill 没空写稿"（发推优先）。

**SLA**：采集跑完 → 4h 内出终稿；终稿生成 → 30min 内决定发或不发（不许"再想想"超时）；发出后按 §8 SOP 跑。

**开工自查（采集前）**：
```
[ ] 昨日已发 ≥1 条原创主推？  No  → 今天 ≥2 条
[ ] 距上次终稿 >24h？         Yes → 警告"流水线断裂"，今天硬目标 ≥1 条
[ ] 有未消费的高分候选？      Yes → 先消费，别急着跑新一轮采集
[ ] 今天在改 Skill？          Yes → 先发 1 条 MVP 再改
```

## 7. 辅助流水线

- **🔥 突发通道**（"突发：[事件]"）：trend-scout 突发模式 → topic-engine 快速出 P0 角度 → tweet-composer 单推 15 分钟内 → 检查点③ → 终稿。全程自动，只在终稿暂停。
- **💬 互动管理**（"互动规划"）：engagement —— Outbound（去别人推文下抢评论位）+ Inbound（自家评论区分级回复）。
- **📊 定期复盘**（"这周数据怎么样"）：performance-review（数据 + 爆款入素材库）→ 优化建议回流 topic-engine / tweet-composer；竞对侧走 competitor-watch。

## 8. 发布后 SOP + 流水线 KPI

终稿交付时把这四步一起给用户，发出后逐步提醒：**T+0** 外链不放主推（移 Thread 末条或首评）· **T+5min** 发首评 · **T+30min** 作者亲自回复 2-3 条评论 · **T+60min** 查触达，低于同类基线记入复盘、**不删推**（错了发更正）。规则依据见 `tweet-composer/SKILL.md` §7。

**落地率 KPI**（performance-review 周复盘算）：`P0 24h 落地率 = 已发推的 P0 候选数 / P0 候选总数`。≥70% 🟢 健康 · 40-70% 🟡 查断点在哪个节点 · <40% 🔴 列出未落地 P0 + 归因（采集失误 / 选题卡住 / 写稿跳过 / 手动叫停）写进周报。

## 9. 指令路由

- "跑一轮" / "跑一遍热点" → 全链：trend-scout（首扫）→ topic-engine → tweet-composer
- "刷新一下" / "扫一下热点" / "深度扫描" / "热点不够" → trend-scout 对应模式 → topic-engine
- "今天发什么" → trend-scout → topic-engine（停在检查点②）；"突发：[事件]" → 突发通道（§7）
- "帮我写推文：[角度]" / "把这篇拆成 Thread" → 路由到 tweet-composer（⚠️ **路由不等于免检**，能不能真跳掉选题看 §1 跳节点权限表）

其余单 Skill 触发词见 README 功能表。
