# 数据复盘 Performance Review

全流水线的闭环节点：所有 Skill 的产出 → **复盘** → 改动反馈回各 Skill。复盘跑完顺手把高表现推文入素材库（§6），素材库反过来喂选题和写作。与 engagement 的分工：它管互动层（评论/关系），本 Skill 管全局（内容策略/增长/对标）。

> **数据源**：Followin MCP 5 工具 — `metrics` / `news` / `signal` / `twitter` / `subscription`。tradfi 标的必传 `asset_type="tradfi"`。
> **账号锚定**：所有 Twitter 调用固定写你的**运营账号** `user_name`，**别用 MCP 登录号、别用 whoami 返回值**——两者常常不是同一个账号，混用会把别人的数据当成你的。

## 0. 直接触发时的自检（本 Skill 可不经 `twitter-ops` 调度器）

⚠️ 用户可能直接说「这周数据怎么样」而不走调度器，那边的初始化闸门**不会执行**。
开工前按 `config.md` §开工四检 逐条走一遍：

**① 账号锚定** = `ACCOUNT`（唯一权威，仍是占位符就停下来让用户填）
**② 目录** = `STATE_DIR`，🔴 不得指向 `/tmp`（硬检查）
**③ 时钟** 一律 shell 现取（`date +%F` / `date +%G-W%V`），全程复用同一组值，**不许凭模型的日期认知推算**
**④ 依赖文件「存在但仍是占位符 / 带 `INIT-STATUS: template-default`」= 视同未配置** → 记 `n/a` + 显式标注

🔴 **四条的完整判据与后果只维护在 `config.md` 一处，本文不复述**——
样板复制到七个文件会给人"全仓已覆盖"的错觉，而实际覆盖的只是最容易复制的那部分。

## Step −1：先读上周的落地清单

跑数据**之前**先看上次复盘产出的改动清单，逐条标 ✅ 已生效 / ⚠️ 部分 / ❌ 没做，"未验证"的单独列警告——否则每周都在提新建议，没人回头看旧的有没有用。

## 采样总则（🔴 作用于本文**全部**步骤，不是只作用于紧跟它的那一步）

**🔴 必须剔转推。** `include_replies=false` **只过滤回复，不过滤转推**——这是两个独立维度，
必须分别判（实测 `@elonmusk` 首页 20 条里 14 条是 `RT @`）。
口径是「非 reply **且非转推**的原创推」。判转推**首选 `retweeted_tweet` 字段非空**（结构判据，2026-07-30 实测更稳）；无该字段回退 `text` 以 `RT @` / `RT@` 开头。

**适用范围逐项点名**（少任何一处，这条规则就等于没写）：

| 环节 | 位置 |
|---|---|
| 对标账号基线 | Step 0 |
| 自家中位 / max / 健康度 / ER | Step 1 |
| Top 3 / Bottom 3 / 类型效果 | Step 2 |
| S/A 级入 `vault.md` | §内容入库 |
| 实现口径（分页 + 三堆拆分） | `references/metrics-guide.md` §1 |
| 离线脚本 | `scripts/tweet_analyzer.py`（已在 `drop_retweets()` 统一处理，三种输入格式共用） |
| 机检 | 报告模板自检 ⑰，frontmatter `retweets_dropped` 必须是实数 |

不剔的后果是**静默产出错误数据**：中位数/ER/Top3 全建在别人的推文上（实测 max 11.1M 是一条 `RT @grok`），
而报告数字齐全、格式正确，看不出问题。
⚠️ 最重的一级是入库：不剔转推会把**一条转推**写进 `vault.md` 当成你自己的可复用爆款句式，
再喂给写作环节——**错误从此长期污染下游**。

> 💡 **`RT @` 只是显式转推。** 引用推（quote）在 API 里是独立推文、算你自己的，不剔。
> 判据只看 `text` 开头，不要扩大到"提到了别人"。

## Step 0：行业基线对照（第一硬规则）

🔴 **WoW 的两个窗口一律自己采，一次采完——不复用 `competitor-watch-$WEEK.json` 里的任何数字。**

这条看起来是在放弃一个现成的省力路径，但那个路径是错的：复用 `this_week`（最多 7 天前采的）
配上自己现采的 `prev_week`，产物就是**两次不同采集拼出来的 WoW**——正是下面「🔁 上周基线一律重扫」
整段在禁止的形态。而且「`scanned_at` ≤8 天」这道闸**抓不到任何东西**：文件名钉死 `$WEEK`，
同一个 ISO 周内间隔最大 6.99 天，必然 ≤8。真正的风险（周一采的对标窗口 vs 周日跑的自家窗口，错位 6 天）
从这道闸底下完整通过。

那份文件仍然值得读，但**只读不参与 WoW 计算的部分**：`top3` 的爆款文本、`best_learnable`、
`industry_verdict` 作定性参照。数字口径一律用本 Skill 这次采的。

采集口径：并行拉 3–5 个同梯队账号的**本周 vs 上周**：日均发推数 / 中位 views / max views。名单在 `../competitor-watch/references/competitor-list.md`；数据量大，走 Agent 子进程 + jq 汇总，别把原始 payload 灌进上下文。

- **🔒 采集铁律：`user_tweets` 必须 cursor 分页翻到窗口起点**（自家和对标都是）——首页只返最近约 20 条，**只拉第一页会漏掉半周推文，中位、ER、Top1 全错**；判定某天"0 发帖"也要翻页确认不是漏抓。分页与汇总写法见 `references/metrics-guide.md`。
- **账号存活性检查**：**先判名单是否仍是占位符**（`@[账号1]` 这类）→ 是则记「未配置，去填 competitor-list.md」**不报停更**；名单已填的前提下，`user_info` 返回 not found **或**最新推距今 >30 天 → 报警「疑似停更/改名，需人工核实 handle」，**禁止标 N/A 了事**（把死号当"数据缺失"会连续多周误判成自己的采集问题）。
- **必须出 WoW Δ%，禁止只列绝对值**——只看绝对值会把"逆势上涨"读成"我们在跌"。
- **🔁 上周基线一律重扫，并与上周报告值并列**：复盘在周中上午跑就**必然截断当天**——上周报告采集时，上周最后半天的推文还没发。拿那个截断快照当基线 = 每周都在和一个被低估的自己比，**系统性高估本周表现**，甚至翻转结论方向（旧值算涨、重扫值算跌）。
  ① WoW **只用同一次采集的两窗对比**；② 三值并列（格式见报告模板 `self_WoW`），注明差异里"窗口截断"与"views 自然增长"各占多少；③ 差异 >10% 且主因是截断时，在数据缺口章节写明。**报告快照是"当时"的真值，不是"那一周"的真值。**
- **高频号兜底**：单日 ≥10 推的账号翻页也够不到上周窗口 → 改用 `twitter(action="search", query="from:账号", time_range=...)` 按窗拉；仍失败标"数据缺失"，**禁止编造**。
- **三类判定**：**普跌**（≥3/5 中位 -10% 以上）= 行业问题不调路径 ／ **普涨但自家跌** = 紧急排查 ／ **分化** = 路径选择问题。逆势上涨的账号**必须单独拆解它本周的爆款**。
- **对标表要同时给「发文量 Δ%」和「中位 Δ%」**：只看中位会漏掉**增量稀释**——加量 +50% 而中位 -18% 是摊薄，不是内容变差。**逆势号还要交叉验互动率**：views 涨 30% 但 Top3 只有个位数点赞 = 分发侧抬升不是内容共鸣，**标为不可复用**，别照抄。

## Step 1：北极星目标 + 健康度 + ER

**目标表（首屏必有）**

> ⚠️ **下表的方括号是「算法」不是「占位符」**——`[当前中位 ×1.3]` 是让你**用本次实测的中位数算出来**，
> 不是等着谁去填一个数字。所以 §0 ④ 的占位符规则**不适用于本表**：
> 按公式算出具体数值填进去即可，**不要因为看到方括号就把整表记 n/a**。
> （否则会形成死循环：表要求"首屏必有"，占位符规则要求"记 n/a"，而下面的未达成分级
> 建在一张 n/a 表上永远无法判定。）
> 只有 `[目标]`（周净增粉）和 `[进阶值]` 是真的要你拍一个数——没拍就写「未设定」并跳过该行的达成判定。

| 维度 | 4 周目标 | 12 周目标 |
|---|---:|---:|
| 周均 views | 本次实测中位 ×1.3 | ×2.5 |
| 中位 views | 本次实测中位 ×1.2 | ×2 |
| >10K 爆款 | ≥1/周 | ≥2/周 |
| 周 ER | 近 4 周实测 ER 中位略上方（= ER floor） | floor ×1.5 |
| 周净增粉 | 未设定则写「未设定」 | 同左 |
| 作者回复率 / 带图率 | 100% | 100% |

附 Δ% 和**健康度 = 中位/平均**（防单条爆款把平均拉高、造成"整体在涨"的错觉）。未达成：4 周没到 → 查硬规则执行率；8 周没到 → 迭代分析；12 周没到 → 战略反思。

**🩺 健康度 <0.70 → 强制腰部诊断**（只报数不动作 = 等于没测）：

1. 列出中位以下的全部条目（views + 标题），看有无共同特征——**不预设它们有缺陷**；
2. **算"去掉 Top2 后的健康度"并二分**（核心判据）：去头 **≥0.85 = 头部驱动型**（腰部均质、基本盘稳，低健康度是爆款够大造成的 → **良性，标 ✅ 不计恶化**）；去头 **<0.85 = 腰部真塌** → 🟡，连续 2 周 → 🔴，必须在 Step 3 产出针对腰部的改动；
3. 单独看尾部（views < 中位 50%）的共同缺陷，给**一条具体动作**（不是"提升质量"这种空话）。

> ⚠️ 不做二分，这条闸会在每次出大爆款时误报"腰部塌了"。**"平均涨、中位跌"有两种方向相反的成因**——腰部塌（坏）与头部变强（好），只看健康度一个数分不出来。

**ER 公式钉死**：`ER = (likes + rt + replies) / views`，**书签不进 ER**（单列 BM/L = 书签/点赞）。报告必须写明口径；跨周对比前核对上周口径一致，不一致就只报本周值、不下 Δ 结论。

**ER floor 按实测水平设**，别照抄"行业优秀 5%"——floor 设成每周必炸的值 = 警报疲劳，整条规则会被无视。取近 4 周实际 ER 中位略上方作 floor，达成后逐级上调。ER < floor → 触发下周互动规划（交给 engagement）。

**🚨 spam 闸 + 三口径**：每次必算 `reply/like`。**>1.0 = 反常**（正常账号 <0.3）→ 报告顶部必须写"ER 不可采信"。

```
ER 原始   = (L+RT+R_all)    / V   ← 上限，含 spam
ER 剔靶标 = (L+RT+R_非靶标) / V   ← 主判据（保留正常帖真评论，只剔靶标帖 replies）
ER 保守   = (L+RT)          / V   ← 下限，全剔 replies
```

逐条算 `reply/like`，**>5 判为疑似 spam 靶标**（>3 会把正常帖划进来，>8 会漏）。**结论用「剔靶标」口径**——保守口径把全周 replies 一刀切掉，连正常帖的真评论也剔了，区间宽到三倍没法判断。靶标清单交给 engagement §2.6 处置。判 spam 的三条证据链见 `references/metrics-guide.md`；要点是 **API 测不出精确比例，且"返回数 < replyCount"在 `has_next_page` 仍 true 时多半只是分页没翻完——必须翻到 `has_next_page=false` 仍显著少于 replyCount 才可判折叠降权**（N-57，与 engagement 的修正表述一致）。

## Step 2：数据分析硬区块

- **内容类型效果对比 + 劣质类型扫描**（按**轴 A 形态**统计；轴 B 角色的配额达成另见 topic-engine）：每个类型设 median 阈值（建议主引擎类型 = 账号整体中位 ×1.5，常规 ×1.0）。🟡 = 达阈值 70–100% 连续 2 周 → 优化；🔴 = <70% 连续 3 周 → 剔除候选、4 周 → 强制剔除。**剔除前确认样本 ≥3 条且非不可抗力**；剔除后配比归零 1 周看整体中位是否回升，误判就恢复。**类型状态跨周表**（上周 → 本周）必出。
- **🎯 单主题集中度**：单一类型/主题周占比 **>60% 🟡 引擎集中**（抗风险差、同主题堆量边际递减）；**>80% 🔴 单引擎依赖**（主题一消退无接棒，必须列为 finding 提给选题环节）。同时标注**连续 ≥3 周 0 条的板块** = 缺口。
- **对标差距**：中位倍数差 + 跨账号共识 Pattern。差距连续 2 周扩大 → 策略反思；对标账号自身中位变动 ≥20% → 更新锚点。
- **算法 5-KPI**：回复/点赞 >0.20 ｜ **BM/L 书签点赞比 >0.15** ｜ 作者回复率 100% ｜ 视频占比 ≥10%（⚠️ **判据待实测**：本模板没有核实过 `twitter(action="user_tweets")` 返回里带不带 media 类型字段——第一次跑时打印一条推文的完整返回，找到 media 字段名后把它写回这里；**在写回之前这一项一律记 n/a**，不许拿猜的字段名去判，也不许因为它常年 n/a 就把整个 5-KPI 当噪音忽略）｜ 外链主推 0%。外加发布后 SOP 执行率（T+5 首评 / T+30 回复 / T+60 复查）。
- **🔄 互动方向**：把自己的 reply 分成**对内**（自己推文下）和**对外**（去别人推文下），报告必带 `对外:对内`，**>5:1 → 🟡 互动精力单向外流**，判断是有意策略还是失控。⚠️ 对标/Tier 1 互动次数**用对外 reply 的 `inReplyToUsername` 分布 + text 开头 `@handle` 兜底判定**（该字段 31% reply 为 null，只靠它会漏 1/3 互动对象，见 metrics-guide §2）——不采集会连续多周误报"0 次互动"，而实际可能早已达标：**"未采集 ≠ 未发生"**。
- **粉丝净增**：`user_info` 跑完**立刻把粉丝数追加进周快照文件并回读确认**；周净增**必须等于该文件最后两条之差**，对不上 = 断档或编造。
- **作者回复率严口径** = 「作者回复过**他人**评论的原推」/ 全部原推，**剔除自评促推**（不占评论位、不算互动）。宽口径能虚高一倍以上。
- 三项的具体测法见 `references/metrics-guide.md`。
- **Top 3 爆款复盘**（成功归因 + 可复制模式）+ **Bottom 3 失败分析**（低于阈值的进失败警示库，三条都要写）。
- **打分-效果回验**（若选题环节有打分）：把候选打分 join 发布后 24h views，出 `日期 | 候选 | 打分 | 24h views | 排名分位`，判断"分高的是否真的表现更好"。连续 2 周高分候选低于当周中位 → 重审权重。样本薄就诚实标"样本不足仅记录"，**别硬下结论**。

## Step 3：学习闭环（≥3 条硬规则）

4 个维度提炼 finding：① 自家 Top3 的共性 ② 逆势对标账号的顶推 ③ 跨账号共识 Pattern ④ 失败警示避坑。

每条 finding 落成一行提议：**改哪个 Skill 的哪一节 + 具体改成什么 + 验证日期**，合成一张表让用户拍板（A 全收 / B 部分 / C 跳过 / D 修改），确认后直接改文件。

违反信号：0 条调整 = 返工；"下周再说" = 不允许；没有验证日期 = 一定会被忘。

## Step 4：写学习日志

追加本周块：落地表 + **上周改动的验证状态**（✅/⚠️/❌）——下次复盘的 Step −1 读的就是它。

## 5. 发布回填

用 `twitter(action="user_tweets")` 拉当日窗口内的**非 reply 且非转推**的原创推文，回填到当天的选题记录（发了什么、对应哪个候选）；24h 后再回填一次 views/likes/rt/replies/ER。用途：算选题落地率、给打分回验供数。回填条数 vs 实测条数不一致就标 ⚠️（匹配漏了，或发的推和候选完全没重叠）。

## 6. 内容入库（复盘完顺手做）

复盘已经把本周推文按表现排过序，入库只是多走一步：**把 S/A 级拆成可复用的东西**。**按 ER 分级不按绝对数**（粉丝在涨，早期推绝对数低但比率可能更高）：S = ER Top 10%（深度拆解）／A = Top 25%（提炼模式）／📌 观察 = ER > 均值 1.5 倍／🚫 避坑 = ER 垫底（**低表现也要记**，否则会重蹈）。

- 单条按 `references/vault.md` 的拆解模板填（话题/角度/开头技巧/结构/钩子/情绪/成功假设 + 可复用句式）。
  🔴 **追加前先按 `tweet_id` 查重**，已在库的只更新数据、不再插一条，并填 `入库` 日期。
  周报窗口与月报窗口重叠（月报覆盖 4 个周报窗口），**同一条推文必然被扫到两次**——
  不去重就会让 `patterns.md` 的「至少出现 2 次」被一条推文自己凑满，
  **一次运气升格成"✅ 稳定模式"**再反哺选题打分。
- 跨条累积的模式、句式、高流量关键词写进 `references/patterns.md`，
  **每月重算一次排名**（🔴 **只重写 patterns.md §三那一张表，其余小节原样保留**——
  按字面理解成"整份重新生成"会抹掉 §六 复用追踪的历史；计数前同样先按 `tweet_id` 去重）；**复用后表现不及原条目 2 次以上就降级**——没有复用追踪，"成功模式"只是事后叙事。
- **日常调用**：写推文前找灵感（按话题搜历史条目 → 3 个方向 + 参考）／验证某个角度过去的表现／取 ER 最高的 5 个开头句式。
- **批量处理**：`scripts/tweet_analyzer.py` 离线跑 —— `api` 格式**同时认 Twitter API v2 与 Followin MCP 两种字段命名**（MCP 的 `viewCount`/`likeCount` camelCase 也读，不会因字段名不匹配静默降级成绝对互动数）；另支持官方归档 `tweets.js` / CSV，自动算 ER、按 Top10%/25% 打 S/A 级、输出 Markdown 报告 + 入库 JSON：`python scripts/tweet_analyzer.py -i tweets.json -f api -o report.md`。首次建库或样本量大时用；日常几十条直接用 MCP 拉。

## 8. 频率与原则

日检 3 分钟（核心指标）／ 周报（Step −1 → Step 4 全跑 + 入库）／ 月报（加：配比对照、涨粉取关比、对标名单升降级、S/A 级归档）。

原则：看趋势不看单点 · ER 优先于粉丝数 · 每次必产出 actionable · 不做虚假归因 · **指标本身不会告诉你它为什么动**（异常先拆成因再下结论）。

上下游：← engagement（互动数据）· competitor-watch（对标基线）／→ 选题（方向）· 写作（策略 + 素材库句式）· engagement（互动优化）。
